# Кейс-стади: Проектирование отказоустойчивого ИИ-бэкенда для Telegram Mini App «Магия Бабушки»

*Приватный коммерческий проект / Исходный код закрыт*

**Технологический стек:** Node.js, Express, OpenRouter API, Supabase (PostgreSQL), React, Vite, Tailwind.

---

## 1. Постановка задачи и технические вызовы

Перед разработкой бэкенда стояла задача развернуть интерактивное психологическое приложение внутри Telegram (Mini App), использующее генеративный ИИ для построения персонализированных текстовых прогнозов. Архитектура решения должна была справляться со следующими критическими вызовами:

- **Нестабильность работы и задержки (Latency) LLM-провайдеров.** Генерация развернутых, качественных текстов через внешние API часто сопровождается сетевыми сбоями, ошибками `429 Too Many Requests` (превышение лимитов) или `5xx Server Errors`. В условиях мобильного использования Mini App это приводило к прерыванию пользовательских сессий.
- **Удержание специфической ролевой модели и контекста.** ИИ должен строго следовать сложной игровой роли (мудрая, загадочная "Бабушка-гадалка"), не скатываясь в клише ассистента ("Я всего лишь языковая модель...") и избегая сухих академических ответов.
- **Проблема согласования грамматического рода в русском языке.** В отличие от английского, русский язык глубоко флективен. Генеративные модели часто путают род глаголов и прилагательных при обращении к пользователю (например, "ты получил" для женщины или "ты сделала" для мужчины), что мгновенно разрушает игровую иллюзию и снижает вовлеченность.

## 2. Архитектура пайплайна генерации

Для решения описанных задач был спроектирован линейный модульный пайплайн обработки запросов. Схема движения данных выглядит следующим образом:

```text
[Telegram WebApp] -> [Express API] -> [Supabase (Контекст/Байо)] -> [Пайплайн OpenRouter API + Fallback] -> [Модуль согласования родов] -> [Ответ пользователю]
```

### Этапы работы пайплайна:

1. **Инициализация запроса и авторизация.** Telegram Mini App отправляет зашифрованные данные инициализации (initData) на Express API, где мидлвари валидируют подпись Telegram.
2. **Получение контекста и профиля.** Из СУБД Supabase (PostgreSQL) извлекается история предыдущих взаимодействий, текущие результаты психологического теста (карта выборов пользователя), а также метаданные (имя, пол пользователя).
3. **Формирование системного окружения (Prompt-архитектура).** На бэкенде динамически собирается финальный промпт для LLM. Он состоит из трех слоев:
   - **System Prompt (Ролевой каркас):** Описание характера "Бабушки", ее лексикона, запретных тем и стилистики повествования.
   - **Few-Shot примеры:** Готовые пары "запрос-ответ", демонстрирующие желаемую структуру ответа, форматирование и длину абзацев.
   - **User Context (Динамические данные):** Вектор ответов пользователя на психологические вопросы и текущий запрос.
4. **Отказоустойчивая отправка (OpenRouter API + Fallback).** Запрос передается в цепочку моделей через OpenRouter SDK с контролем таймаутов.
5. **Лингвистическая постобработка.** Сгенерированный текст пропускается через модуль согласования родов, который корректирует глагольные окончания и местоимения.
6. **Выдача клиенту.** Очищенный и адаптированный текст возвращается на фронтенд в Telegram WebApp.

## 3. Реализованные инженерные решения

### 3.1. Система умного перехвата ошибок (Multi-Level Fallback)

Для борьбы с нестабильностью сетевых API и сбоями LLM-провайдеров на уровне Express-мидлварей была внедрена каскадная система переключения моделей:

- **Контроль таймаутов (Request Timeout):** На каждый запрос к OpenRouter API накладывается жесткий лимит времени (например, 8000ms).
- **Идемпотентность и повторные попытки (Retry Pattern):** При получении сетевой ошибки или таймаута система автоматически выполняет до двух повторных попыток к основной модели.
- **Каскадный переклич (Failover/Fallback):** Если основная модель (например, Claude 3.5 Sonnet) недоступна, возвращает статус `429` или `5xx`, Express-контроллер мгновенно переключает пайплайн на резервную альтернативную модель (например, GPT-4o-mini), сохраняя системный контекст.
- **Локальный алгоритм безопасного вывода:** В случае полной недоступности внешних шлюзов (сетевой таут-аут) активируется локальный генератор заглушек, который выдает пользователю нейтральный атмосферный текст, связанный с его текущим шагом, предотвращая "зависание" интерфейса.

### 3.2. Автоматизация согласования родов на бэкенде

Для обеспечения 100% грамматической точности обращений к пользователю на русском языке бэкенд использует комбинированный метод:

1. **Динамическая инъекция в системный контекст.** При получении пола из Telegram API (или после прохождения короткого опроса) в системный промпт инжектируется жесткое правило:
   `"Обращайся к пользователю строго в [мужском / женском] роде. Пример: 'ты пришел и увидел' / 'ты пришла и увидела'."`
2. **Лингвистическая постобработка (Regex-микромодуль).** Сгенерированный текст перед отправкой проходит через легковесный парсер, который проверяет критические маркеры (например, "был/была", "рад/рада") и при необходимости корректирует их на основе зафиксированного в сессии пола пользователя. Это устраняет редкие галлюцинации LLM, когда модель сбивается с контекста посреди длинного ответа.

## 4. Технические метрики и результаты

Внедрение архитектурных решений позволило достичь высоких показателей надежности для пользовательской аудитории:

- **Отказоустойчивость системы (Uptime генерации): 99.9%.** За счет использования каскадного переключения моделей на уровне OpenRouter SDK ни один сбой конкретного ИИ-провайдера не привел к падению сервиса.
- **Стабильность вывода:** Настройка Express-мидлварей и оптимизация token-limit (ограничение максимального количества генерируемых токенов) полностью исключили обрывы предложений на полуслове.
- **Грамматическое соответствие:** Внедрение постобработки гарантировало 100% точное попадание в грамматический род пользователя во всех сгенерированных сессиях.
