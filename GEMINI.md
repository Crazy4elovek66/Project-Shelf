# Git & Deployment Workflow (Vercel)

В этом проекте используется разделение окружений Vercel на **Production** (ветка `main`) и **Preview** (любые другие ветки). 
Перед началом выполнения задач из `task.md` или прямого запроса пользователя ты обязан определить целевой режим деплоя по кодовому слову/тегу.

## Сценарии работы

### Сценарий 1: `[PREVIEW]` (Кодовые слова: `preview`, `превью`, `тест`, `черновик`)
Используется по умолчанию для новых фич, редизайна и экспериментов.
1. Проверь текущую ветку (`git branch --show-current`).
2. Если ты находишься в ветке `main` (или `master`), **НЕ ДЕЛАЙ** коммиты туда. Создай и переключись на новую ветку формата `preview/<краткое-название-задачи>` (например, `git checkout -b preview/hero-section`).
3. Выполни задачи из `task.md`, отметив выполненные пункты `[x]`.
4. Сделай коммит и пуш в эту ветку (`git push -u origin preview/<название>`).
5. В финальном отчете сообщи, что изменения отправлены в **Preview-окружение** Vercel (ветка `preview/...`), а основной домен (`idleon.pro`) не затронут.

### Сценарий 2: `[PROD]` (Кодовые слова: `prod`, `прод`, `релиз`, `в бой`)
Используется для срочных фиксов, мелких правок текста или финального выката проверенных изменений.
1. Переключись на основную ветку (`git checkout main`) и подтяни актуальные изменения (`git pull origin main`).
2. Выполни задачи из `task.md`, отметив выполненные пункты `[x]`.
3. Сделай коммит и пуш напрямую в `main` (`git push origin main`).
4. В финальном отчете подтверди, что изменения ушли напрямую в **Production** (`idleon.pro`).

## Правило безопасности (Защита от случайного релиза)
- Если в `task.md` или в твоем промпте **не указан** ни тег `[PREVIEW]`, ни тег `[PROD]`, **всегда выбирай сценарий `[PREVIEW]`** по умолчанию. Никогда не пушь изменения в `main` без явного указания `PROD`.
